# 决策记录

## 2026-10-29 · v1.1.0 不引入 WeUI 组件包

**决定**：借 WeUI 的结构语言（cell 列表、8rpx 间距梯度、按压态），
但不安装 WeUI 组件包，样式全部映射到本项目已有的双主题 token。

**理由**：
- 项目已有一套调好的 `--surface-0..5` / `--text-1..4` 深色双主题体系，
  并在 `app.wxss` 注释里记录了踩过的坑（切 tab 黑闪、box-sizing、
  按钮凸出）。
- WeUI 自带浅色 + 微信绿，直接引入会顶掉这套 token，等于推翻约 96KB
  现成样式重写。

**代价**：不能直接复用 WeUI 的现成组件，需要自己写样式（已实现
`.cells` / `.cell` / `.tap`）。

**如果将来要改**：只有用户明确要求「完全按微信原生浅色」时才重新评估，
那时是一次完整改版，不是增量。

## 2026-10-29 · 进度条动画改 transform，保留 width 兜底

**决定**：`.bar-fill` 动画用 `transform: scaleX(var(--bar))`，但 WXML
里同时保留 `width: X%`。

**理由**：过渡 `width` 每帧触发 layout，是 v1.0.x 卡顿主因。但 `@supports`
和 CSS 变量在 WXSS 里的支持度不 100% 确定，只写 `transform` 一旦不被
支持，进度条会变成比例错误。两条都写、用 `@supports` 分流最稳。

**代价**：WXML 里表达式重复了一遍，略微冗长。

## 2026-10-29 · 卡片入场动画只加前 3 个

**决定**：`rise-in` 只给每个主页的前 3 个卡片加。

**理由**：页面里卡片数量 13~60 个。全加会在页面加载瞬间几十个元素
同时动画，与「不卡顿」的目标直接矛盾。

## 2026-10-29 · 施工范围限定 5 个 tabBar 主页

**决定**：本次只改 dashboard / courses / tasks / healthhub / settings。

**理由**：用户确认的推荐方案。先验证方案有效性再推全量，降低已上线
项目的回归风险。

**遗留**：11 个非 tabBar 页面仍在用旧 `width` 写法，靠兜底正常工作。
